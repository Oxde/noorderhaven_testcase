Technical case · AI engineer assessment

Noorderhaven claims agent

An agentic intake system that reads claim emails (Dutch, English, mixed) with their PDFs and photos, checks them against the policy API, looks for fraud signals, approves what is safe and hands everything else to a human, with the reasoning attached.

The LLM extracts, code decides.
One LLM call turns an email into a structured fact sheet. Every coverage check, payout, routing decision and outgoing email is deterministic, tested Python. Customer text is untrusted data: an injected instruction can at most produce a wrong fact, never an approval.

Design choices behind the diagram

  • One LLM call per email, for extraction only. Each yes/no judgement (gradual damage, abroad, third party, other bank account, injection) comes with a verbatim evidence quote, so a handler can check it.
  • Model chain, cheapest first. A schema failure counts as a failed attempt: retry, then the next model. The strongest model (Sonnet, about 25× the cost) is only used when the cheap ones fail.
  • Standard library only. Nothing to install, no supply-chain surface, and it runs anywhere with Python 3.9+.
  • Sequential decisions, parallel I/O. Extraction and policy lookups run in parallel. Decisions run in received order, so duplicate and repeat-claimant checks see claims registered earlier in the same run.
  • Retries are safe. Every write carries a deterministic Idempotency-Key, so a retry after a timeout returns the original record instead of creating a second one.
  • The audit trail is the record. Every step per claim is logged with its API attempt count. The mock API's own write log confirms what was actually written.

Safety

Where a human stays in control

RiskHow it is limited
Wrong automatic payoutOnly net ≤ €1,000 with complete documents, a verified sender, the policy found by number, and no risk indicator, late report or missing photos. Handlers sample these. Eval gate: 0 false auto-approvals.
Prompt injectionThe LLM decides nothing. Regex and LLM detection both send the claim to fraud review, and the review page shows the injected passage with a warning. Both case injections (in an email and hidden in a PDF) and a reworded Dutch one in the holdout were caught.
Data leakMail only goes to the original sender (checked in the pipeline and again in the review server). Identity requests carry no policy data. Third parties get nothing. Thread links across different senders are refused.
Rejection without a humanRejections are always drafts until a handler approves them on the review page. Eval gate: 0.
AI outageThe keyword fallback never decides in normal mode. Every claim goes to a handler, with no letter sent.
Duplicates from retriesDeterministic Idempotency-Keys. The write log shows each claim and decision exactly once.
Review page abused from another siteJSON-only POSTs, plus Origin and Host checks (CSRF and DNS rebinding).
Evaluation

How we know the decisions are right, and where that claim is weaker

Case set, 40 claims

100% action match and 100% payout match against an answer key written from the rulebook before the code. All 5 safety checks at 0.

Read that number carefully. Two rules were adjusted after the first eval on these same claims. The first untuned run scored 97.5%.

Blind holdout, 12 new claims

Written by an agent that never saw the code, with answers from the rulebook alone. 91.7% strict, 100% counting accepted alternatives, payouts 5/5, safety 0.

The one strict miss: no photos above €500 went to a handler, where the author preferred asking the customer for photos.

Independent review

A separate reviewer session rebuilt an answer key without seeing the code: 37/40 same action. The 3 differences are rulebook gaps (the photos rule, a mistyped policy number). It also found the fallback safety gap, now fixed and tested.

Robustness

Chaos on in every run: 170 API calls, about 20% retried, 0 failed writes. Also tested: KIE down, an idempotent re-run, and no-LLM mode (see docs/robustness.md).

GapReading

Honest status

What is cut, fake or untested

Cut on purpose

  • Vision on photos. The photos are captioned placeholders, so we only count them.
  • A real mailbox and multi-turn reminders. Replies are merged and reminder drafts listed, but nothing polls an inbox.
  • LLM-written letters. Templates cannot promise money or leak data.
  • Logins, multiple handlers, a database. State is JSON files; the mock API is the system of record.

Fake or untested

  • No email is really sent and no money moves (mock outbox).
  • The review page has no automated browser test; it was checked by hand and through its API.
  • The final run replayed LLM answers cached from the live run minutes earlier (same prompt and models, 40 real calls, 1.19 credits).
  • Explicit --no-llm mode is a developer mode. On unseen emails the keyword reader misses things, which is why it never decides in normal mode.

What breaks first at 200 claims a day

  1. LLM rate limits and latency. KIE allows 20 requests per 10 s, and upstream errors happen. Fine for 200 a day, but a 09:00 burst queues. Next: a persistent work queue with per-provider rate limits.
  2. The flaky policy API. Retries cope, but a crash mid-run needs a durable outbox to resume. Idempotency keys already make a restart safe.
  3. Handler capacity. About 65% of claims need a human here. The value comes from tuning what is safe to automate, driven by the review log's override rate.
  4. JSON files as state. Concurrent handlers would clash. Move to a database.

Next steps, in order

  1. A persistent per-claim ledger checked before deciding, so a re-run never auto-approves a claim an earlier run left for a handler.
  2. A reminder flow for info requests, with real inbox threading.
  3. A persistent queue, a database, and multi-user review with logins.
  4. A larger labelled eval set from handled claims, with the safety checks as a CI gate.
  5. An LLM second opinion on thin "gradual" and "outside Europe" evidence, shown to the handler, never deciding.
  6. A vision check on real photos.
